# CLAUDE.md

이 파일은 이 작업공간(Claude Code / Claude Desktop)에서 Roblox Studio 작업을 할 때의 가이드입니다.

> **버전**: Ver 1.5 (2026-09-17 개정)
> 개정 근거: 2026-09-16 실제 플레이스(`Operate_System(OS) test`)에서 수행한 테스트에서 검증된 내용만 남기고,
> 실행할 수 없던 수식·추상 구조는 실행 가능한 절차로 교체했습니다. 이전 버전은 `backup/` 및 GitHub에 있습니다.

## 0. 기본 원칙

1. **한국어**: 모든 응답, 보고서, 코드 주석, 커밋 메시지를 한국어로 작성합니다.
2. **근거 우선**: "될 것이다"가 아니라 "확인했다"로 말합니다. 실행 여부, 컴파일 결과, 문서 출처로 뒷받침되지 않은 주장은 추측이라고 명시합니다.
3. **되돌릴 수 있게**: 모든 변경은 백업 → 변경 → 테스트 순서로 진행합니다. 되돌릴 방법이 없는 작업(플레이스 게시, 파일 삭제, DataStore 쓰기)은 사용자 승인 없이 하지 않습니다.
4. **범위 지키기**: 요청받은 것만 합니다. 요청 범위를 넘는 개선은 **제안**하고 사용자 판단을 기다립니다.
5. **모르면 조사**: 기억에 의존하지 말고 context7이나 공식 문서로 확인합니다. Roblox API는 자주 바뀝니다.

## 1. MCP 사용 기준

| MCP | 용도 | 사용 시점 |
|-----|------|-----------|
| Roblox Studio | 플레이스 조회/편집/실행, 콘솔 확인 | Roblox 작업 전반 (필수) |
| context7 | Roblox 공식 문서 확인 (`/roblox/creator-docs`) | API 동작, 실행 규칙을 단정하기 전 (필수) |
| sequential-thinking | 문제 핵심 파악, 우선순위 결정 | 문제가 여러 갈래일 때 |
| playwright | 웹 문서/페이지 직접 확인 | context7로 부족할 때만 |

- 체크리스트 통과용으로 MCP를 형식적으로 호출하지 않습니다. **필요할 때 쓰고, 쓰지 않았으면 쓰지 않았다고 보고**합니다.
- playwright는 프로젝트 폴더에 `.playwright-mcp/` 로그를 만듭니다. 작업이 끝나면 삭제합니다.

## 3. 저장소 설정

```lua
-- 백업용 저장소: 코드를 고치기 전 원본을 복제해 두는 곳
local 백업_저장소_사용 = true
local 백업_저장소_위치 = game.ServerStorage

-- 분석용 저장소: 분석 산출물(구조 기록 등)을 남기는 곳
local 분석_저장소_사용 = false
local 분석_저장소_위치 = game.ServerStorage
```

- 사용 플래그가 `false`면 해당 저장소를 만들지 않습니다. 백업 플래그가 `false`면 **코드 편집 자체를 보류**하고 사용자에게 알립니다.
- 위치가 비어 있거나 <@엑세스>에 없으면 Claude가 엑세스 목록 중 하나를 골라 쓰고, 어디에 만들었는지 보고합니다.
- 분석 산출물은 기본적으로 플레이스가 아니라 `claudedocs/` 문서로 남깁니다(플레이스를 불필요하게 늘리지 않기 위함).

## 4. 작업 시작 전 체크리스트

### 체크리스트
- [ ] 이번 작업에 필요한 MCP가 응답하는가?
- [ ] <@엑세스> 목록의 서비스가 존재하는가?
- [ ] **이 플레이스가 Team Create(공동 편집) 세션인가?** → 콘솔의 `joined live editing session` 또는 사용자 확인
- [ ] **내 변경이 어떻게 저장되는가?** → 초안(Drafts)인지, 즉시 클라우드 반영인지, 로컬 파일인지
- [ ] 요청에 필요한 위치가 <@엑세스> 목록에 있는가?
- [ ] 요청에 게임 설정 활성화가 필요한 서비스(HttpService의 HttpEnabled, DataStore의 API 접근 등)가 있다면 현재 켜져 있는가?

### 통과 실패 시
1. 작업을 시작하지 않고, 통과하지 못한 항목의 원인을 분석합니다.
2. 사용자에게 원인과 필요한 조치를 알려주고 요청합니다.
3. 사용자 응답 후 다시 확인합니다. **최대 3회**까지 반복하고, 그래도 안 되면 작업을 중단하고 상황을 보고합니다.

> Team Create 항목이 중요한 이유: 공동 편집 세션에서는 인스턴스 생성이 곧바로 클라우드 플레이스에 반영될 수 있고,
> 스크립트 수정은 초안으로 남아 Commit 전까지 서버에 적용되지 않습니다.
> 이걸 모르면 "저장하지 않았으니 안전하다"는 잘못된 보고를 하게 됩니다. (2026-09-16에 실제로 그런 오류를 냈습니다.)

## 5. 작업 흐름

```
이해 → 계획 → (편집 시) 백업 → 구현 → 테스트 → 보고
```

1. **이해**: 요청에서 불확실한 부분을 먼저 정리합니다. 사용자 정보로 채울 수 없는 부분은 <@9. 문제 해결>의 판단 절차로 직접 판단하고, 판단한 내용을 보고에 명시합니다.
2. **계획**: 작업이 여러 개면 사용자가 준 우선순위를 따르고, 없으면 의존 관계가 적은 것부터 처리합니다. 독립적인 조회는 병렬로 실행합니다.
3. **백업**: <@6. 코드 작성 규칙>의 백업 절차.
4. **구현**: 한 번에 한 작업. 진행 중 발견한 다른 문제는 기록만 하고 현재 작업을 끝냅니다.
5. **테스트**: 작업 하나가 끝날 때마다 테스트합니다. 문제가 있으면 해결한 뒤 다음 작업으로 갑니다.
6. **보고**: <@13. 보고 형식>.

### 작업 시 주의사항
- **전역/로컬**: 여러 체계에서 쓰일 코드만 공용(ModuleScript)으로 만들고, 나머지는 쓰는 곳 안에 둡니다.
- **과도한 작업 금지**: 단순한 요구에 큰 구조를 만들지 않습니다.
- **추측 금지**: 실패를 만나면 원인을 확인한 뒤 고칩니다. 테스트를 비활성화하거나 검증을 건너뛰어 통과시키지 않습니다.

## 6. 코드 작성 규칙

### 백업 (편집 전 필수)
편집 대상 스크립트(또는 그 최상위 모델·폴더, 서비스 디렉터리 제외)를 <@백업_저장소_위치>에 복제합니다.

**이름 형식**
- `코드이름_상위부모이름_서비스이름_타임스탬프`
- 상위부모가 서비스 자신이면 `코드이름_서비스이름_타임스탬프`
- 예: `ShopSystem_Wrappers_ServerStorage_20260916074101`

**검증**: 백업 후 원본과 소스가 같은지 비교하고, 자식 객체·속성이 있으면 그것까지 복제됐는지 확인합니다.

### 사용자의 검증
코드 작성이 끝나면 사용자에게 보여주고 승인/거절/수정 제안을 기다립니다.
**예외**: 사용자가 "먼저 실행하고 사후 보고"를 명시적으로 지시한 경우. 이때도 **백업은 반드시 만들고**, 무엇을 왜 바꿨는지와 되돌리는 방법을 보고에 포함합니다.

### 코드 품질
- **필요한 것만 인덱싱**: 전체 순회 대신 필요한 집합만 조회합니다.

```lua
-- 나쁜 예: 전체 순회
for _, v in game:GetDescendants() do
    -- code
end

-- 좋은 예: 대상을 좁혀서 조회
for _, v in game.ServerScriptService:GetDescendants() do
    if v:IsA("Script") then
        -- code
    end
end
```

- **재사용 가능한 코드는 함수로**: 같은 판정이 두 번 나오면 함수로 분리합니다.
- **부분 완성 시 중간 테스트**: 긴 코드는 부분별로 확인하며 진행합니다.
- **불완전한 코드 금지**: TODO 주석, 빈 함수, "나중에 구현"을 남기지 않습니다.

### 최적화 절차
1. 코드 전체를 읽고 동작을 파악합니다.
2. 결과가 같은지 확인하면서 재구성합니다. 재구성 전 코드는 백업으로 남아 있어야 합니다.
3. 재구성본과 원본을 **같은 입력으로 비교 테스트**합니다(<@10. 시뮬레이션>).
4. 2번에서 더 바꿀 것이 없으면 종료합니다. 보통 1~2회면 끝납니다. **바꿀 이유를 못 찾으면 그대로 두는 것이 최적화입니다.**

### 작성 체크리스트
- [ ] 200줄 안에 들어오는가? (넘으면 역할별로 나눌 수 있는지 검토)
- [ ] 존재하지 않는 객체를 참조하지 않는가? (`WaitForChild` 대상이 실제로 있는지 확인)
- [ ] 컴파일되는가? (`loadstring`으로 확인 가능)
- [ ] 필요한 함수가 모두 있고 서로 연결되는가?
- [ ] 클라이언트-서버 상호작용이 있다면 <@7. 보안 규칙>을 통과하는가?

## 7. 보안 규칙

### 객체 배치 기준
| 구분 | 의미 | 배치 |
|------|------|------|
| 서버 사이드 | 서버만 접근 | ServerScriptService, ServerStorage |
| 클라이언트 사이드 | 해당 클라이언트만 접근 | StarterPlayerScripts, StarterGui |
| 공유 사이드 | 양쪽 접근 | ReplicatedStorage |
| 서버 감독 공유 사이드 | 공유하되 서버가 접근을 통제 | ReplicatedStorage의 RemoteEvent/RemoteFunction + 서버 검증 |

**민감한 값(키, 토큰, 잔액, 권한 정보)은 서버 사이드에만 둡니다.** ReplicatedStorage의 ModuleScript 내용은 클라이언트가 전부 읽을 수 있습니다.

### 핵심 원칙: 서버가 판정한다
**클라이언트에서 하는 검사는 편의 기능이지 보안이 아닙니다.** 클라이언트 코드와 그 코드가 보내는 값은 전부 조작될 수 있다고 가정합니다.
클라이언트에서 하는 검사는 **서버에서 똑같이 다시** 해야 합니다.

### RemoteEvent / RemoteFunction 서버 검증 항목
받은 인자 하나하나에 대해 아래를 확인합니다. (2026-09-16 이 플레이스의 실제 코드에서 전부 실제 결함으로 확인된 항목입니다.)

- [ ] **타입**: `type(x) ~= "number"`, `typeof(x) ~= "CFrame"` 등으로 먼저 거릅니다. 클라이언트는 테이블·nil·Instance를 보낼 수 있습니다.
- [ ] **존재**: 조회 결과가 nil이면 즉시 `return`합니다. (경고만 찍고 계속 진행하면 다음 줄에서 nil 인덱싱 오류가 납니다.)
- [ ] **소속**: 클라이언트가 보낸 Instance는 **허용된 폴더의 자손인지** 확인합니다. 확인하지 않으면 복제된 아무 Model이나 복제해 갈 수 있습니다.
- [ ] **범위**: 위치·수량·가격은 서버가 계산한 한계와 비교합니다. 정상 클라이언트의 실제 동작 범위를 먼저 측정해 여유를 둡니다.
- [ ] **NaN/무한대**: `if v ~= v then return end` — NaN은 모든 비교가 false라 거리 검사를 그냥 통과합니다.
- [ ] **권한**: 그룹/랭크/팀 조건은 서버에서 다시 확인합니다(`GetRankInGroup`은 `pcall`로 감쌉니다).
- [ ] **빈도**: 플레이어별 쿨다운을 둡니다. 검증 실패로 끝나는 요청에는 쿨다운을 소모시키지 않습니다.
- [ ] **기본값**: 속성이 없을 때의 기본값을 정합니다. 프로젝트에 이미 기본값 규칙이 있으면 그것과 맞춥니다.

```lua
-- 검증 패턴 예시
Event.OnServerEvent:Connect(function(player, itemId, cframe)
    if type(itemId) ~= "number" or typeof(cframe) ~= "CFrame" then return end
    local item = AllowedFolder:FindFirstChild(tostring(itemId))
    if not item then return end
    for _, v in {cframe:GetComponents()} do
        if v ~= v then return end -- NaN 거부
    end
    if (nextAllowed[player] or 0) > os.clock() then return end
    nextAllowed[player] = os.clock() + COOLDOWN
    -- 여기부터 실제 처리
end)
```

### 비밀 값 취급
- 웹훅 URL, API 키를 스크립트 소스에 넣지 않습니다. `HttpService:GetSecret()`(Secrets 저장소)을 사용합니다.
- 이미 소스에 들어간 비밀은 **지워도 플레이스 버전 기록에 남습니다.** 발급처에서 폐기(재발급)해야 해결됩니다. 코드로 해결할 수 없으므로 사용자에게 알립니다.

### 클라이언트 측에서 할 일
클라이언트 스크립트(StarterPlayerScripts의 LocalScript)는 **입력 편의와 즉시 피드백**만 담당합니다.
이상 징후를 서버에 보고할 수는 있지만 그 보고 자체도 조작될 수 있으므로, **서버는 보고 없이도 독립적으로 판정**해야 합니다.
클라이언트가 민감한 데이터를 서버로 되돌려 보내 비교하는 구조는 만들지 않습니다(조작 가능하고, 민감 데이터를 클라이언트에 두게 되는 문제도 생깁니다).

## 8. 코드 분석 체계

### 먼저: 그 코드가 실제로 실행되는가
분석 전에 실행 여부를 확인합니다. 죽은 코드를 고치느라 시간을 쓰지 않기 위함입니다.

| 확인 | 방법 |
|------|------|
| Script 실행 위치 | `RunContext`가 Legacy면 Workspace/ServerScriptService에서만 실행. Server면 ReplicatedStorage에서도 실행되지만 클라이언트에 복제되므로 권장하지 않음 |
| 비활성화 | `Enabled == false` |
| 참조 여부 | ModuleScript는 `require`하는 곳이 있는지 검색 |
| 도달 가능성 | RemoteEvent가 ServerScriptService/ServerStorage 안에 있으면 클라이언트는 접근할 수 없음 |

### 우선순위
- **함수**: 다른 스크립트와 공유 > 함수끼리 공유 > 다른 함수를 호출 > 재귀 > 일반
- **이벤트 핸들러**: 클라이언트 입력을 받는 핸들러 > 사용 함수가 많은 핸들러 > 연결이 많고 긴 핸들러 > 일반
- **변수**: 다른 스크립트와 연결 > 함수와 연결 > 위치 저장 > 일반

### 기록 방식
각 항목에 대해 (1) 어디와 연결되는지 (2) 요청과 관련 있는지를 기록하고, 구조는 트리로 표현합니다.
조건을 중간까지만 충족하면 충족한 데까지 기록하고, 최종 분석에서 그 기록을 참고합니다.
분석 결과가 사용자의 요청과 전혀 다르면, 사용자가 알려준 추가 스크립트 위치를 참고해 범위를 넓힙니다.

## 9. 문제 해결

### 핵심 파악
1. 발견한 문제들을 각각 구체화합니다.
2. 문제들 사이의 관계를 트리로 그립니다(공통 원인이 있으면 부모 노드로).
3. 연결이 많은 것, **실제로 실행되는 코드에 걸린 것**, 악용·피해가 큰 것 순으로 우선순위를 정합니다.
4. 가장 위를 핵심으로 정합니다.

### 부작용 점검 (해결책을 정한 뒤)
해결에 필요한 요소 중 **오히려 문제를 키우는 것**이 있는지 확인합니다.
- 검증을 강화하면 정상 사용자가 막히지 않는가? → 정상 경로의 실제 범위를 먼저 측정합니다.
- 통신 형식을 바꾸면 반대편 코드가 깨지지 않는가? → 한쪽만 고쳐서 해결되는 방법을 우선합니다.
- 고쳤지만 실제로는 해결되지 않는 것은 아닌가? (예: 이미 유출된 비밀) → "해결된 것처럼 보이는 조치"를 경계합니다.

### 판단
사용자가 정보를 주지 않은 부분은 직접 판단하되, 판단할 때마다 다음 세 가지를 확인하고 **판단 내용과 근거를 보고에 남깁니다.**
- 이 판단이 사용자 요청의 목표와 직접 연결되는가?
- 요청을 다르게 이해한 것은 아닌가?
- 판단 근거를 보고에 쓸 수 있는가?

### 해결 후 검토
문제의 핵심이 실제로 풀렸는지, 다른 부분이 깨지지 않았는지 확인합니다. 검토는 테스트 결과로 합니다.

## 10. 시뮬레이션 (실제 환경 없이 검증하기)

Play 모드를 돌릴 수 없거나(실제 DataStore 쓰기 위험 등), 필요한 데이터가 플레이스에 아직 없을 때 사용합니다.

### 절차
1. **수정한 실제 소스**를 `loadstring`으로 불러옵니다(따로 옮겨 적은 복사본이 아니라 실제 소스여야 의미가 있습니다).
2. `setfenv`로 가짜 `game`, `require`, 이벤트 객체를 주입합니다.
3. 핸들러를 직접 호출해 정상 케이스와 악용 케이스를 모두 넣습니다.
4. **원본 코드도 같은 케이스로 돌려** 차이를 비교합니다(수정이 실제로 무엇을 막았는지 증명).
5. 임시 Instance는 부모를 지정하지 않고 만들고, 끝나면 `Destroy`합니다. 플레이스를 변경하지 않습니다.

```lua
local fn = assert(loadstring(대상스크립트.Source))
setfenv(fn, setmetatable({
    game = 가짜game,
    require = function(m) return 가짜모듈[m] end,
}, { __index = getfenv(0) }))
local module = fn()
```

### 주의: 테스트 픽스처 함정
테스트가 실패하면 **코드를 의심하기 전에 테스트부터 계측**합니다. 실제로 겪은 사례:
- `Instance.new("Shirt").Name`은 `"Shirt"`가 아니라 `"Clothing"`입니다. `FindFirstChild("Shirt")`로 찾는 코드와 어긋납니다.
- 기대값을 잘못 적어 정상 동작을 FAIL로 판정한 경우.

### 한계 명시
시뮬레이션으로는 네트워크 복제, 실제 그룹 API, 물리 상호작용을 검증할 수 없습니다.
**"시뮬레이션 통과"는 "동작 확인"이 아닙니다.** 보고에 한계를 함께 적고, Play 모드 테스트가 필요하면 그렇게 말합니다.

## 11. Roblox Studio MCP 운영 지식 (2026-09-16 확인)

| 상황 | 내용 |
|------|------|
| `execute_luau`로 객체를 ServerStorage 등에 넣기 | **불가**. Capabilities 제한으로 reparent가 거부됩니다. 스크립트 생성·수정은 `multi_edit`을 사용 |
| `execute_luau`의 `require` | 일부 모듈에서 Capabilities 오류. 필요하면 `script_read`로 소스를 읽어 판단 |
| `ChangeHistoryService:TryBeginRecording` | 중간에 오류가 나면 기록이 **열린 채로 남습니다**(`IsRecordingInProgress`가 true). 기록 ID를 잃으면 닫을 수 없고 Undo가 이상해집니다 → 되도록 쓰지 말고, 열렸다면 사용자에게 Studio 재시작을 안내 |
| `script_read` 부분 읽기 | `should_read_entire_file=false`일 때 `start_line_one_indexed`와 `end_line_one_indexed_inclusive`가 **둘 다** 필요 |
| Play 모드 전환 | DataStore에 쓰는 스크립트가 있으면 실제 데이터가 바뀝니다. 실행 전 확인하고 사용자 승인을 받습니다 |
| 콘솔 | `get_console_output`에 Team Create 참가, 플러그인 경고 등 중요한 정보가 있습니다. 작업 전후로 확인합니다 |

## 12. 자기 상태 점검

### 사용량 확인 (순서대로 시도)
1. **세션 로그 계산 (기본, 즉시 가능)**: 현재 세션 기록 파일에서 토큰 사용량을 직접 계산합니다.
   - 경로: `~/.claude/projects/<프로젝트 경로>/<세션 ID>.jsonl`
   - 각 줄의 `message.usage`에서 `input_tokens`, `output_tokens`, `cache_creation_input_tokens`를 합산하고, `timestamp`로 최근 5시간 창을 잘라냅니다.
2. **터미널 직접 생성**: 필요하면 새 터미널/셸을 만들어 위 계산이나 CLI 조회를 실행합니다. 이것도 1번 방법에 포함됩니다.
3. **사용자에게 요청**: 요금제의 정확한 잔여 한도(%)는 로컬에 저장되지 않고 CLI에도 비대화형 조회 명령이 없습니다(2026-09-16 확인). 정확한 수치가 필요하면 사용자에게 `/usage` 결과를 물어봅니다.

**하지 않는 것**: 사용자의 브라우저·로그인 세션을 자동으로 조작해 수치를 긁어오는 행위. 계정 조작 위험이 이득보다 큽니다.

### 판단
- 사용량은 5분위로 나눠 [매우 좋음, 좋음, 평균, 나쁨, 매우 나쁨]으로 봅니다. 사용자가 기준을 주면 그 기준을 씁니다.
- 재설정 창은 5시간입니다. **남은 창 시간 대비 소비 속도**로 "지금 속도로 계속하면 창이 끝나기 전에 한도를 쓰는가"를 판단합니다.
- 정확한 한도를 모를 때는 **상대 지표**(이번 창의 응답 수, 토큰 합계, 창 시작 시각)를 보고하고 "정확한 잔여량은 확인 불가"라고 분명히 말합니다.

### 중단 절차
한도가 부족하거나 사용자가 지정한 중단 시각이 가까워지면:
1. 진행 중인 작업을 **되돌릴 수 있는 상태**로 마무리합니다(중간 상태로 두지 않습니다).
2. 보고서를 작성합니다(<@13. 보고 형식>).
3. 남은 작업과 다음에 이어갈 지점을 적습니다.

## 13. 보고 형식
