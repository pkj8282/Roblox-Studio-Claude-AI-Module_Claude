```lua
local function countOwned(player: Player, id): number
	local count = 0
	for _, item in player.Backpack:GetChildren() do
		if item:GetAttribute("Id") == id then count += 1 end
	end
	local tool = player.Character and player.Character:FindFirstChildOfClass("Tool")
	if tool and tool:GetAttribute("Id") == id then count += 1 end
	return count
end

function ShopSystem.Purchase(self: ShopSystem, playerInstance: Types.PlayerInstance, itemTypeId: number)
	if type(itemTypeId) ~= "number" then return end
	local itemData = PurchaseableItemDatas.ShopItems[itemTypeId]
	if not itemData then
		warn("아이템이 현재 존재하지 않음: " .. tostring(itemTypeId))
		return
	end
	local payType = itemData.PurchaseType == 0 and "Coin" or "Token"
	if itemData.Cost > playerInstance.Data[payType] then
		warn("재화 부족: " .. payType)
		return
	end
	local limit = itemData.ItemInstance:GetAttribute("PurchaseLimit") or 1
	if countOwned(playerInstance.Player, itemData.ItemInstance:GetAttribute("Id")) >= limit then
		warn("아이템 구매량 한계 도달")
		return
	end
	playerInstance.Data[payType] -= itemData.Cost
	playerInstance:ExposeUserWalletData()
	itemData.ItemInstance:Clone().Parent = playerInstance.Player.Backpack
end
```

사용자는 보고서 작성 후 PC를 꺼도 된다고 허락했지만, **종료하지 않았습니다.**

이유 (07:35 실행 중인 앱 확인 결과):
- `RobloxStudioBeta` — `Operate_System(OS) test`가 열려 있음. 저장되지 않은 변경이 있는지 확인할 수 없음 (이번 테스트는 플레이스를 바꾸지 않았지만, 테스트 전에 사용자가 편집한 내용이 있을 수 있음)

- `Orca` — 이 세션을 실행하는 호스트일 수 있음

Windows에서 `shutdown /t N`(N>0)은 강제 종료(`/f`)가 함께 적용되어 위 앱들의 미저장 데이터가 사라질 수 있습니다. 되돌릴 수 없는 손실 위험이 테스트 종료라는 목적보다 크다고 판단했습니다. 또 PC가 꺼지면 사용자가 터미널의 최종 보고를 볼 수 없게 됩니다.

직접 종료하시려면 저장 후 다음 명령을 실행하세요:
```powershell
shutdown /s /t 0
```

**[문제의 핵심 파악]** 1차에서 찾은 결함들을 트리로 연결:
```
R: 서버가 클라이언트 입력을 신뢰 (노드 5개, 활성 코드 포함 → 핵심)
 ├ SystemSpawnVehicle (활성)   위치 무검증 → 맵 어디든 차량 생성      ← 실제 악용 가능
 ├ UniformScript (잠재)        클라이언트가 보낸 아무 Model이나 복제  ← 배치 즉시 악용 가능
 ├ ShopSystem (활성)           타입/존재 검증 누락 → 서버 오류
 ├ ERS_Call (활성)             임의 데이터를 모든 클라이언트에 중계
 └ Discord 웹훅 Script         소스에 비밀 토큰이 하드코딩됨
S: 미완성/테스트 코드 (_SEC, SSS.Script×2, Shop_Main) → 영향이 작아 우선순위 낮음
```
1차에서는 ShopSystem만 봤지만, 같은 유형을 **실제로 실행되는 서버 코드 전체**로 넓혀 추적했습니다. 차량 키트 같은 서드파티 코드는 제외하고, 실행 여부는 RunContext/Enabled/위치로 거른 결과 7개 핸들러가 나왔습니다.

**[필요하지만 문제를 복잡하게 만드는 요소]**
1. 검증을 너무 빡빡하게 걸면 정상 사용자가 막힘 → 클라이언트 배치 로직(`StarterGui.SpawnVehicle.Main.Handler:125-165`)의 실제 범위를 읽고 여유를 둠
2. NaN 좌표는 모든 비교가 false라서 거리 검사를 **통과해 버림** → 별도 검사 필요
3. 통신 형식을 바꾸면 클라이언트 코드도 고쳐야 함 → 서버 쪽에서만 검증
4. 웹훅 토큰은 소스에서 지워도 백업본과 플레이스 버전 기록에 남음 → 코드를 고치면 해결된 것처럼 보이는 착시만 생김 → 수정하지 않고 사용자 조치로 보고
5. 플레이스 저장/게시는 되돌리기 어려움 → 하지 않음

**[판단 검토]** 사용자 요청은 "발견한 것을 이어가라"이고, 발견한 것은 입력 검증 결함입니다. 같은 유형을 추적하고 수정하는 것은 요청의 직접적인 연장선이라고 판단했습니다.

## 6.4 적용한 수정

### SystemSpawnVehicle (43줄 → 67줄)
- `vehicleName`이 string인지 검사하고, `VehicleHitboxes`에 있는 차량만 허용 (클라이언트 버튼 노출 조건과 같음)
- `isValidSpawnCFrame`: HumanoidRootPart 기준 수평 거리 ≤ `hitbox.Size.X*0.5 + 20`, 수직 거리 ≤ `hitbox.Size.Y + 60`, CFrame 12개 성분에 NaN이 있으면 거부
  - 근거: 클라이언트 배치 거리 = `size.X*0.5 + 3`, 천장 탐색 +20, 바닥 탐색 −(25+size.Y), 여기에 이동/지연 여유를 더함
- 쿨다운은 검증을 통과한 뒤에 설정 (서버 검증에 실패한 정상 사용자가 9초를 기다리지 않도록)

### ShopSystem (57줄 → 66줄)
- `itemTypeId`가 number인지 검사, 없는 아이템이면 `return`
- `PurchaseLimit` 기본값 1 — `PurchaseableItemDatas.lua:33`의 기존 기본값과 같음
- 보유 수량 계산을 `countOwned` 함수로 분리. `count=1; count > limit`을 `count=0; count >= limit`으로 바꿨는데 판정 결과는 같음

### UniformScript (86줄 → 127줄)
- `isAllowedOutfit`: 셔츠/바지 템플릿과 헬멧/조끼 Model이 `LockerSetting/<팀>/복장/<복장>`의 내용과 **정확히 일치할 때만** 허용
- `hasTeamAccess`: 클라이언트(`LockerGui.MainScript:154-164`)의 그룹/랭크 조건을 서버에서 다시 확인 (`GetRankInGroup`은 pcall로 감쌈)
- 플레이어별 1초 쿨다운 (PlayerRemoving 때 정리), Head nil 방어
- **클라이언트↔서버 통신 형식은 바꾸지 않음**
